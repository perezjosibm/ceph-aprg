To capture and analyze S3 benchmark traffic generated by `elbencho` against Ceph RGW, you can use `tcpdump` or `tshark` on the client host, then analyze the traffic in Wireshark or via automated scripts.

---

### Part 1: Instrumenting Wireshark for S3 Benchmarks

#### 1. Capture Network Traffic

Run `tcpdump` on the client host during an `elbencho` run to capture raw PCAP data without GUI overhead:

```bash
# Capture HTTP traffic to/from Ceph RGW (replace 8080 with your RGW port)
sudo tcpdump -i any host <RGW_IP> and port 8080 -w elbencho_s3_run.pcap

```

> **Handling HTTPS/TLS:** If your RGW endpoint uses HTTPS, export `SSLKEYLOGFILE` prior to running `elbencho` so Wireshark can decrypt the payload:
> ```bash
> export SSLKEYLOGFILE=/tmp/tls_keys.log
> elbencho --s3endpoints "https://rgw:443" ...
> 
> ```
> 
> 
> In Wireshark, load the key log under **Preferences -> Protocols -> TLS -> (Pre)-Master-Secret log filename**.

#### 2. Key Wireshark Filters for S3 Metrics

* **S3 Request/Response Latency (`http.time`):**
```text
http.response.code == 200

```


*Add `http.time` as a column:* Right-click any HTTP response packet $\rightarrow$ **Field Occurrence** or **Apply as Column** for `http.time`. This shows the exact duration (in seconds) between the client sending the HTTP request and RGW returning the response.
* **Filter by S3 HTTP Methods:**
```text
http.request.method == "PUT" || http.request.method == "GET"

```


* **Identify Ceph RGW Errors / Slow Ops:**
```text
http.response.code >= 400 || http.time > 0.1

```



#### 3. Analyzing Benchmark Data

* **I/O Graphs:** Navigate to **Statistics $\rightarrow$ I/O Graphs**.
* Plot 1: Set Y-axis to `SUM(http.time)` / `AVG(http.time)` to view latency curves over time.
* Plot 2: Set Y-axis to `Bytes/Tick` (with Y-Unit set to `Bits/s` or `Bytes/s`) to visualize throughput dips during benchmark phases.


* **HTTP Request Summary:** Navigate to **Statistics $\rightarrow$ HTTP $\rightarrow$ Requests** to view itemized HTTP method distribution (PUT, GET, DELETE, Multipart).
* **Automated Extraction via `tshark`:** Extract per-request latency data to a CSV for processing:
```bash
tshark -r elbencho_s3_run.pcap -Y "http.response" \
  -T fields -e frame.time_epoch -e http.request.method -e http.response.code -e http.time \
  -E header=y -E separator=, > s3_latency_results.csv

```

### Part 2: Impact of Size (`-s`) and Block (`-b`) Arguments

In `elbencho`, **`--size` (`-s`)** defines the overall size of an individual S3 object, while **`--block` (`-b`)** defines the chunk/buffer size used per transfer call.

```bash
elbencho -s <object_size> -b <chunk_size> --s3endpoints ...

```

#### Performance Effects Matrix

| Scenario | `--size` (`-s`) | `--block` (`-b`) | Performance Characteristics | Ceph RGW / RADOS Behavior |
| --- | --- | --- | --- | --- |
| **Small Objects / Small Block** | Low (e.g., `4k`) | Low (e.g., `4k`) | **High IOPS / Low Throughput.** Latency dominated by HTTP overhead, authentication, and index lock competition. | Generates high RGW Bucket Index log updates and OSD metadata updates per transaction. |
| **Large Objects / Singlepart** | High (e.g., `64m`) | Match Size (e.g., `64m`) | **High Throughput / Low IOPS.** Minimizes HTTP/S3 metadata overhead by uploading the entire object in a single HTTP PUT. | Direct streaming into RADOS OSD striping without multipart staging. |
| **Large Objects / Small Block** | High (e.g., `1g`) | Low (e.g., `4k` or `64k`) | **Poor Performance / High Overhead.** Forces micro-buffering or excessive chunked HTTP transfer overhead. | Creates severe socket-write bottlenecking on the client and high CPU usage per MB on RGW. |
| **Large Objects / Multipart** | High (e.g., `1g`) | Medium (e.g., `8m` - `16m`) | **Optimal Throughput.** Triggers S3 Multipart Uploads (MPU), allowing parallel part uploads across threads. | Aligns cleanly with Ceph's internal `rgw_max_chunk_size` (default 4MB) and OSD stripe patterns. |

#### Key Differences & Rules of Thumb

1. **Singlepart vs. S3 Multipart Upload (MPU):**
* When `-s` is equal to `-b`, `elbencho` performs a standard S3 `PUT` request.
* When `-s` is larger than `-b`, `elbencho` automatically uses S3 Multipart Uploads. Each chunk defined by `-b` is sent as an independent `UploadPart` request.
* *Note:* S3 requires part sizes in Multipart Uploads to be **at least 5MB** (except for the last part). Setting `-b` below `5m` during a multipart upload will cause S3 API rejections.


2. **Matching Ceph RGW Internal Alignment:**
* Ceph RGW breaks objects down into 4MB chunks internally (`rgw_max_chunk_size`).
* Setting `-b` to **4M, 8M, or 16M** minimizes buffer copy overhead, memory reallocation, and socket fragmentation on RGW daemons, producing the cleanest throughput numbers.
